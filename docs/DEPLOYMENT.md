# Windows 开发与 Ubuntu 部署

## 第一次接入原 Ubuntu

原 Ubuntu 目录可能在导出 Windows 调试包后继续发生修改，不能直接覆盖，也不要在运行中的目录执行 `git reset --hard` 或 `git clean`。

1. 确认原程序绝对路径、启动用户、单机/团队模式、端口和服务管理方式。
2. 在旁边新建独立 Git 克隆目录。比对两侧源码；原导出包的 `BUILD-MANIFEST.json` 可在本地作为历史校验参考，但不是完整原始源码或 Git 历史。
3. 比对并保留 Ubuntu 独有修改，测试通过后提交到 main。
4. 使用独立测试数据、测试端口和新建的 Linux 虚拟环境做验证。不要让测试实例和正式实例同时写同一套数据库或项目文件，也不要复制正式运行队列启动测试服务。
5. 等所有渲染任务结束，停止原服务，备份代码、配置和业务数据，再迁移到已验证的 Git 目录。保留原目录作为回滚备份。
6. 配置原有服务管理器指向新目录，沿用正确的端口和团队模式；验证后再开放访问。

配置只迁移真实 `config.json`，不要用示例文件覆盖。配置中的绝对路径、下载器和 FFmpeg 路径需按 Ubuntu 实际情况检查。

## 日常开发

```bash
git switch main
# 修改、测试
git add <本次修改的代码文件>
git diff --cached
git commit -m "说明本次修改"
git push origin main
```

个人开发统一使用 main，测试后推送，必要时标记稳定版本。私有仓库可使用 Git Credential Manager 或 SSH 认证；不要在代码或远程 URL 中嵌入令牌。

Windows 已包含运行环境，下载后运行 `start_windows.bat`。旧版应用的更新检查不认识新增的运行包目录，升级到本版本时请停止应用，在终端执行 `git pull --ff-only origin main` 后重新启动。后续即可继续使用新版更新入口。Windows 运行包变化后应关闭程序并重新双击启动，以载入新环境；Ubuntu 忽略该运行包并沿用 Linux 虚拟环境。

## 后续 Ubuntu 更新

团队版管理员可进入管理后台的 **系统更新**：先“检查更新”，再“手动更新此服务器”。
“提交并推送更新”会把当前服务器代码提交并推送到 GitHub，其他机器仍需检查并手动更新。
页面显示当前分支、提交版本、双方领先提交数、未提交文件，以及重启状态。
普通成员不能使用这些管理操作；服务器需为 Git 克隆目录并配置好 GitHub 认证。
首次安装该后台入口时，先按下面的终端流程更新并重启一次，之后即可在网页操作。

以下流程只适用于已经完成首次迁移的 Git 部署目录。

1. 记录 `git rev-parse HEAD`，确认 `git status --short` 没有未处理的代码改动。
2. 确认所有批量、单镜和队列任务已结束。停止正式服务，备份配置及业务数据；代码启动可能迁移数据结构。
3. `git fetch origin`，检查本次差异，再运行 `git pull --ff-only origin main`。出现分歧时先合并，不强制覆盖。
4. 如依赖清单变化，在 Linux 虚拟环境重新安装依赖；运行测试。
5. 使用原服务管理方式启动，检查 `/api/health`、页面、项目读取、节点连接及一次小规模生成。
6. 如失败，停止服务并切回记录的提交。如果数据已发生不兼容迁移，还需要恢复同批备份的数据与依赖环境。

常规 Git 更新不会跟踪或覆盖被忽略的运行数据；首次迁移或未来新增同名受跟踪文件仍需检查冲突。GitHub 不是业务数据备份工具。

## 公开前检查

确认完整 Git 历史不含密钥或私人素材；核实内置技能、示例图片、工作流和依赖授权；为自有代码选择许可证；补齐真实 Ubuntu 安装验证。完成后再将仓库转公开。
